变更一：新增 Phase 1.5——标注持续维护子系统

插入位置：第十四章，Phase 1 与 Phase 2 之间（原 14.3 与 14.4 之间）

动机：原文档在 14.1 节承认标注可行性是核心假设，在附录 B 提及“与 Paper/Folia 上游的持续同步”，但未提供标注资产随 Minecraft 版本演进的维护策略。Mojang 每次大版本更新（约 12-18 个月）平均重构 15-30% 的内部方法签名。若无自动化维护机制，每次上游更新将导致 Phase 0-2 的标注资产以每年 20-30% 的速度衰减，使长期维护成本不可控。

规格：

```
14.3.5 Phase 1.5：标注持续维护子系统（与 Phase 1 并行，独立交付）

目标：交付一套自动化工具链，使标注资产在 Minecraft 版本更新时的
      衰减率低于 5%/年。

组件 A：方法签名变更检测器（MSD）
  - 输入：旧版 Minecraft 反编译源码 + 新版 Minecraft 反编译源码
  - 输出：变更方法列表，按影响程度分级：
    · Level 0（无影响）：方法体未变，或变更不涉及读写集相关逻辑。
      自动迁移旧标注。
    · Level 1（签名变更）：方法重命名或参数重排。
      若旧标注存在，自动生成新标注草稿（需人工确认）。
    · Level 2（语义变更）：方法读写集行为改变。
      标记为“需重新标注”，列入人工审查队列。
  - 核心技术：基于 ASM 的字节码差分 + 方法内数据流摘要比对。
  - 预期自动化覆盖率：Level 0（40-50%）+ Level 1（20-30%）= 60-80% 
    的方法可自动迁移。

组件 B：标注回归测试运行器
  - 在 CI 流水线中集成，每次提交触发。
  - 运行流程：
    1. 加载最新标注库。
    2. 在测试世界中运行 2000 tick 回放。
    3. 对每个标注的方法，使用 RW-Set Integrity Checker
       （12.4节）验证实际访问与声明的读写集一致。
    4. 若不一致，CI 失败，输出差异报告。
  - 此运行器确保：标注不会因代码变更而“静默失效”。

组件 C：标注覆盖率仪表板
  - 可视化展示：
    · 每个子系统的标注覆盖率（已标注方法数 / 总热点方法数）
    · 标注“债务”趋势（Level 2 待审查方法数随时间变化）
    · 上次 Minecraft 版本更新后的标注迁移进度
  - 作为项目健康度的核心指标。

交付物：
  - 方法签名变更检测器
  - CI 集成的标注回归测试运行器
  - 标注覆盖率仪表板

团队：1名工具链开发者 + 1名标注工程师（与Phase 1共享）

注：Phase 1.5 不阻塞 Phase 2 启动。它作为独立交付流，
    在 Phase 1 中后期开始，持续运行至 Phase 3 及以后。
```

变更二：增强 DAG 构建超时降级机制

修改位置：第四章 4.4 节、第十六章 16.1 节

动机：原文档 2.2 节将 DAG 构建时间从 30ms 优化到 500μs 的路径依赖三项良性假设（任务空间均匀分布、桶间依赖边 <1%、网格单元 K<10）。4.4 节给出了分层执行算法但未定义构建阶段本身的超时保护。16.1 节提到“DAG 构建超时→降级为传统单线程执行”但未指定阈值或检测机制。在红石计算机、密集实体农场等极端场景下，DAG 构建可能意外超时，缺乏精确的超时保护将使单次超时演变为连续 tick 超时（雪崩）。

规格：

在 4.4 节“DAG 执行引擎”之前，新增 4.3.1 节：

```
4.3.1 DAG 构建时间预算与降级

DAG 构建阶段必须在一个硬性时间预算内完成。若预算耗尽，
构建过程必须产生一个合法（即使不是最优）的 DAG。

时间预算：BUILD_BUDGET = 2ms（占 50ms tick 预算的 4%）

预算执行机制：
  1. 桶内构建阶段（4.2节）：
     - 每个桶的构建是独立的，可并行进行。
     - 主线程在分发桶构建任务后，以 100μs 为间隔轮询完成状态。
     - 若累计耗时达到 1.5ms 且有桶未完成构建：
       对未完成桶执行快速路径：
         a. 终止桶内细粒度网格索引构建
         b. 将该桶内所有任务视为一个粗粒度串行块
         c. 该块内部按任务 ID 字典序排序执行
         d. 该块与其他桶的依赖边使用粗粒度读写集
            （该桶内所有任务的读写集之并集）
  
  2. 全局合并阶段（4.3节）：
     - 若合并耗时达到 0.5ms 且未完成：
       跳过传递冗余边消除（4.3节步骤3），
       直接使用包含冗余边的 DAG 进行分层。

降级记录：
  - 每次触发快速路径或跳过优化，递增降级计数器。
  - 若连续 10 个 tick 触发降级，生成警告日志并
    建议管理员检查服务器中的极端密集结构。
  - 降级不影响正确性——粗粒度 DAG 仍是合法拓扑排序，
    仅降低并行度。

检测与诊断：
  - /nebula dag-stats 命令新增字段：
    · build_time_p50/p99/max（最近 100 tick 的构建耗时分位数）
    · degraded_ticks_ratio（触发降级的 tick 比例）
    · slowest_bucket（最近一次构建中最慢桶的坐标和任务数）
```

同步修改 16.1 节错误分类表：

```
| DAG构建超时 | 快速路径降级（4.3.1节） | 自动恢复；连续10次降级触发管理员警告 |
| DAG构建失败（异常） | 当前tick回退传统单线程执行 | 记录严重错误；下个tick重试正常构建 |
```

变更三：新增 VAP 插件认证计划

插入位置：第十三章，新增 13.7 节

动机：原文档在结语中承认“社区生态——技术成功不等于采用成功”是系统性风险，但未在 VAP 设计中给出应对措施。Folia 的经验表明，插件生态的迁移意愿是并行服务端采用率的决定性因素。需要在设计阶段就植入生态建设机制，而非在 Phase 3 才考虑。

规格：

```
13.7 星云插件认证计划

13.7.1 认证级别

| 认证级别 | 要求 | 标识 | 性能收益 |
|---------|------|------|---------|
| Nebula Ready | Level 0 兼容运行，无运行时错误 | 绿色徽章 | 无（插件串行执行） |
| Nebula Optimized | Level 1 适配，关键数据结构使用 @ManagedState | 银色徽章 | 部分并行加速 |
| Nebula Native | Level 2 适配，使用原生数据流 API | 金色徽章 | 完全参与 DAG 并行 |

13.7.2 认证流程

1. 插件开发者提交认证申请（GitHub Issue 模板）。
2. 自动化 CI 流水线运行：
   - Level 0：在星云测试套件中运行插件 10000 tick，
     检测 VAP 警告日志、虚拟线程超时、沙箱降级事件。
   - Level 1：运行并发压力测试（10 线程同时访问
     @ManagedState 字段），检测 MVCC 冲突率和合并函数正确性。
   - Level 2：验证任务提交的读写集声明完整性
     （使用 12.4 节完整性检查器）。
3. 审核通过后，插件列入星云官方兼容性目录。
4. 认证每年重新验证（或在 Minecraft 大版本更新后触发）。

13.7.3 兼容性目录

在星云官方网站维护一个可搜索的插件兼容性数据库：

字段：
  - 插件名称、版本
  - 认证级别
  - 已知限制（如“Level 1 适配，但 /reload 时需重新加载状态”）
  - 最后验证日期
  - 性能数据（MSPT 贡献，在标准测试负载下测量）

服主可通过 /nebula plugins 命令在游戏内查询已安装插件的认证状态。

13.7.4 激励措施

- 认证插件在官方目录中优先展示。
- 金色徽章插件的开发者获得星云项目的技术推广支持。
- 向主要插件（EssentialsX、WorldGuard、LuckPerms 等）的维护者
  主动提供适配协助（在 Phase 2 预算中预留适配工程师时间）。
```

变更四：定义 T2/T3 保真度等级

修改位置：第十五章 15.1 节，fidelity-tier 配置项说明

动机：原文档定义了 T0 和 T1（主要在第十一章 Random 部分），但配置文件中出现了 T0-T3 四个等级，语义未定义。

规格：

在 15.1 节 fidelity-tier 配置项下补充：

```yaml
nebula:
  # 时序保真度等级
  # T0（严格确定性）：所有子系统保持与原版逐位一致。
  #   - Random 序列严格确定（影子执行保证）
  #   - AI 使用当前 tick 最新数据（无弱依赖）
  #   - 适用于：生电服务器、需要精确红石时序的场景
  #
  # T1（统计确定性）：放宽 Random 序列的逐位一致性。
  #   - Entity.random 使用独立种子（线程本地）
  #   - AI 启用弱依赖优化（允许 1 tick 新鲜度延迟）
  #   - 红石、物理、方块更新保持 T0 级别确定性
  #   - 实体随机决策统计分布一致，但序列顺序可能不同
  #   - 适用于：生存服务器、对随机序列无逐位要求的场景
  #
  # T2（宽松确定性）：进一步放宽。
  #   - 实体物理碰撞响应允许偶尔的顺序差异
  #     （在 SCC 无法在单 tick 内完全展开时）
  #   - AI 感知使用上一 tick 快照
  #   - 红石保持 T1 级别（微步骤完整性不变）
  #   - 适用于：高玩家数生存服务器、小游戏服务器
  #
  # T3（最大并行度）：尽最大努力并行，不保证确定性。
  #   - 所有子系统启用最大并行度优化
  #   - 红石微步骤可能跨 tick 分割（极极端场景）
  #   - 适用于：不需要确定性的创意服务器、压力测试
  fidelity-tier: T0
```

同步更新 16.2 节降级路径：

```

T1 -> T2: MSPT连续30秒>50ms
```

```
F.2 星云相对于 Folia 的核心差异

Folia 的哲学是空间分治：
  - 将世界划分为区域，每个区域独立 tick
  - 区域内保持单线程顺序
  - 跨区域交互通过特殊调度处理
  - 问题：跨区域红石、实体穿越区域边界时，顺序不确定

星云的哲学是因果保持：
  - 理解状态之间的信息依赖关系
  - 仅在没有因果依赖的任务之间并行
  - 有因果依赖的任务保持其依赖顺序
  - 结果：任何位置的并行都保持因果一致性

关键推论：
  - Folia 的并行度受制于“区域”的划分粒度。
    区域过大则并行度不足，区域过小则跨区协调开销激增。
  - 星云的并行度受制于任务之间的实际数据依赖。
    理论上，只要两个任务不操作同一坐标/实体，它们就可以并行，
    无论它们在空间上是否属于同一“区域”。

F.3 Folia 已知问题清单（星云设计对照）

以下问题来自 Folia 的公开 issue 跟踪器和 Luminol 补丁集，
星云在设计上对其逐一应对：

| Folia 已知问题                        | 星云应对措施              | 参考章节 |
|--------------------------------------|--------------------------|---------|
| 跨区域红石信号不确定                 | DAG 依赖边捕获跨桶交互    | 4.1, 5.4|
| 实体跨区域传送时数据竞争             | 每 tick 按实体位置分配桶  | 6.3     |
| 光照更新重复条目                     | DAG 依赖边自动去重        | 10.2    |

F.4 星云不是 Folia 的替代品
```
